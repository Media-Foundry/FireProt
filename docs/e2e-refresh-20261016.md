# Complete invocation refresh: DiamondHill, 2026-10-16

This study refreshes each connected model route on DiamondHill. Precision is a
separate gfx1100 deployment with [its own native baseline](precision-setup.md).
The refresh is still running; only completed, accepted comparisons belong in
the results table. It does not qualify unimplemented OpenFold2 or ESMFold v1.

## Measurement boundary

- Frozen Rust CLI: SHA-256
  `1f5365ecf4824f1b2d99ca88bcc25d36be57f434a78f1e6ff17f5bb95a55dce0`.
- Complete invocation: immediately before spawning the Rust inference command
  through observing its exit, including full asset verification, process startup,
  loading, preprocessing, prediction, export and acceptance. Benchmark comparison
  and subsequent independent evidence collection are outside this timer.
- Three paired repetitions in AB/BA/AB order, with a fresh worker per invocation.
  Both arms use the same frozen CLI. The reported ratio divides the two arm
  medians; individual paired ratios are retained separately.
- HIP6, physical PCI `0000:8e:00.0`, gfx90a MI250. GPU identity and process
  isolation checks remain enabled. No concurrent FireProt GPU performance jobs.
- Filesystem and GPU caches are unflushed. Qualified kernels are already built;
  this is not a first-install/build benchmark. DiamondHill-sourced asset
  transmission to Precision is paused at a complete-file boundary during timed
  model queues. Starting at 2026-10-16 16:32 UTC (2026-10-17 locally), an independent
  local-host → Precision relay downloads the same pinned official ESMFold2
  assets, with complete hashes before installation. That relay reads no
  DiamondHill files and runs no process on DiamondHill. The frozen specifications'
  "asset transfer paused" wording refers to the original DiamondHill sender.
- The native reference is each adapter's qualified original-math route under
  FireProt's common launcher. This does not mean an unmodified upstream command
  or a uniform latest-source checkout: profiles pin model-specific worker and
  operator revisions. Protenix shares fast construction and preprocessing
  changes between arms. Every input/checkpoint/profile is pinned in the evidence.

The original historical Mini worker timer and AtlasFold packaged-request timer
excluded some of these costs. Their old ratios are not directly comparable to
this complete invocation boundary. No incremental ratios are multiplied.

## Acceptance and independent checks

Rust validates each invocation and each pair before continuing. The collector
then rehashes accepted metadata and outputs, verifies invocation bindings and
physical-device identity, and compares all exported archive members.

- pLMs: every exported array must match official native execution using the
  same batch grouping, and repeated outputs must be byte-identical. This does
  not assert that batched and singleton execution have identical rounding.
- AtlasFold, OpenFold3 and ESMFold2: all arrays and complete native CIF files
  must be byte-identical, including repeated runs within each arm.
- Protenix Mini/Mini-ESM/Tiny: unchanged `protenix-established-1e-3-v1` coordinate
  and summary-confidence gates, exact structural metadata, and CIF atom-identity
  checks. Floating confidence arrays remain diagnostics and can differ.
  Within-arm byte equality is reported separately; it is not assumed.
- Protenix Base: the user-approved aligned all-atom RMSD ≤0.1 Å and summary
  confidence maximum difference ≤0.001, after matching CIF atom identities.
  Each run must also match its frozen same-arm output reference. The original
  stricter generic coordinate comparison is retained as a separate diagnostic;
  its threshold is not changed.

Mini N1000's three paired aligned RMSDs are 0.0000911–0.0001036 Å; N1536's
are 0.0001008–0.0001372 Å. Their summary-confidence differences are at most
0.00000382 and 0.0000268 respectively. Floating PAE/PDE arrays are not exact:
paired maximum differences reach 0.01356/0.04903 at N1000 and 0.05727/0.07038 at
N1536. Repeated candidate outputs also have small differences. These observations
pass the established policy and must not be described as bitwise equality or
as experimental-coordinate accuracy.

## ESMFold2: remaining time outside the model forward

The accepted logs already contain nested wall-clock timers. Full hashes of their
`predictions.json` and `supervisor.json` match each acceptance receipt. The frozen
worker's timer implementation matches the maintained source byte-for-byte.
No additional inference or profiling was performed for this analysis.

| Boundary/component, median seconds | Native | Optimized |
| --- | ---: | ---: |
| Complete invocation | 368.783 | 178.666 |
| Model forward, including bundled ESMC | 270.853 | 81.682 |
| Worker request minus model forward | 20.581 | 20.394 |
| Supervisor minus worker request | 43.254 | 43.490 |
| Complete invocation minus supervisor | 33.528 | 33.520 |

The last three rows are medians of **per-invocation differences**; component
medians need not sum exactly to the complete-call median. The worker timer
starts after imports, immediately before model construction, and includes loading,
input building, inference and native/archive export. The supervisor timer starts
near worker spawn, after preflight and execution-identity capture. The outer
timer also includes the remaining startup and final acceptance work.

These are timing boundaries, not isolated stage measurements. In particular,
the roughly 77 seconds outside the worker request must not be labelled entirely
as checkpoint hashing or Python imports. Its similar size in both arms makes
verification/startup/acceptance a concrete profiling priority alongside the
remaining 82-second model forward. An optimization must preserve full artifact
verification and outputs. [Six-run timing evidence](../provenance/e2e_refresh_esmfold2_timing_boundaries_20261016.json).

## Preserved failures and corrections

The first OpenFold3 refresh stopped before inference because its old environment
inventory was stale. An audit recaptured the **same full specification**:
157,886 entries, 14 added and 14 removed system-library names, and 58 changed
entries including aliases. Changes cover host OS libraries/loader cache and the
unused top-level Rust bridge. Model Python environments and qualified operator
bundles were unchanged. The actual OpenFold3 operator bridge is a separate,
unchanged recovered artifact. Both retry arms pin the same new inventory;
coverage, source settings and numerical checks remain unchanged. The failed
attempt is retained and has no speedup result.
[Full inventory diff](../provenance/e2e_refresh_openfold3_inventory_20261016.json).
The diff's `captured_pending_review` status describes the capture stage; the
review and equal-arm repinning are recorded by the retry's `preparation.json`.

The initial AtlasLM refresh request was a **singleton**, despite a historical
directory/specification name containing `b4`. Its published label was corrected;
the valid singleton timing is 14.839 → 13.118 s, 1.131x. A separate true B4
request retains seed102 and explicitly verifies four inputs/outputs. An earlier
preparation assertion expecting seed101 rejected that setup before GPU work.

Collector v2 also incorrectly demanded byte-identical repeated Protenix Mini
outputs. Version 3 preserves this diagnostic and uses Mini's established Rust
policy for acceptance. It retains exact-byte requirements for the other models.
The original collector and its failed assertion remain available in the run
directory; neither inference nor its numerical gates was modified.

The first AtlasFold N1536 comparison also rejected an incorrect treatment
declaration. Its chunked Torch reference already loads the same Rust policy
bridge as the optimized route, while the preparer incorrectly declared that
bridge as candidate-only. The recorded reference selected 528 chunked Torch
attention calls, registered no HIP implementation and loaded no GPU extension.
The correction removes only this nonexistent difference; shared bridge identity
remains protected by the ordinary equality check. Both profiles, model routes,
workloads and numerical gates are unchanged. The failed trial is retained and
all three pairs are rerun into `atlasfold-n1536-declaration-retry`.

### Run the measured OpenFold3 composition

The latest OpenFold3 result uses a frozen experimental composition. The ordinary
`configs/diamondhill/openfold3-hip-fused.json` example does not select all of those
optimizations. On the prepared DiamondHill deployment, use the exact measured
request/profile with a fresh run ID and output directory:

```bash

  "$RUN_ROOT/openfold3-n1536-refreshed-env/candidate-profile.json"
```

This request selects HIP6 and strict FP32 N1536/R3/D200/S1. The complete current
environment inventory remains required; subsequent host updates can invalidate

equality when benchmarking. The request is a measured workload, not a general
recipe for a different protein length, precision or sampling schedule.
