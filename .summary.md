# FireProt project summary

Updated: 2026-10-16. Includes the 2026-10-16 standalone pLM E2E refresh; folding refresh is in progress.

## Scope and architecture

FireProt is an AMD-specific protein folding inference framework focused on long
sequences. Rust owns commands, workload validation, artifact verification,
operator policy, builds, process/GPU supervision and numerical acceptance.
Upstream Python/PyTorch retains model execution; qualified HIP/CK libraries
accelerate selected tensor operations. Rewriting orchestration in Rust does not
itself establish GPU speedup.

Connected folding paths: Protenix Mini/Mini-ESM/Tiny/Base, AtlasFold with AtlasLM,
OpenFold3/OpenBind-0, and Biohub ESMFold2 with bundled ESMC. Standalone commands
cover ESMC, ESM2, ESM3 sequence inference and AtlasLM. OpenFold2 and original
ESMFold v1 remain future adapters. Protenix and OpenFold3 are separate models.

Work on `master`. Keep upstream Protenix as an independent checkout. Weights,
CCD resources, generated outputs and build artifacts remain outside Git.
Repository declarations are English; user-facing discussion is Chinese.
License scope and third-party exceptions are defined by the repository license
files, not by this summary.

## Entry points

```bash
cargo build --release -p fireprot-cli -p fireprot-runtime -p fireprot-bridge --locked
target/release/fireprot inspect REQUEST.json
target/release/fireprot infer REQUEST.json PROFILE.json
target/release/fireprot esm REQUEST.json PROFILE.json
target/release/fireprot atlaslm REQUEST.json PROFILE.json
```

Requests pin model/input/checkpoint/resource identities and scientific settings.
Profiles select the host environment and workers. Use fresh run IDs and output
directories. `scripts/infer.sh` and `scripts/smoke.sh` delegate to Rust.
Existing DiamondHill profiles contain absolute paths and are not portable
installation presets. See [README](README.md), [architecture](docs/architecture.md)
and [installation](docs/installation.md).

## Latest ESMC findings

The qualified route combines HIP RoPE/SwiGLU, exact checkpoint placement and
Rust host scheduling/monitor improvements. The latest optimized GPU profile
attributes approximately 80% of device kernel time to GEMM and 9% to attention.
This does not establish hardware-counter compute/memory saturation.

- Installed CK GEMM increased B4 warm-forward time by about 7.3% and failed
  exact-output acceptance. All 48 tested direct tile/projection combinations
  also failed byte equality. These are tested configurations, not a universal
  conclusion about CK.
- Larger B16 grouping gave only 1.0025x E2E versus optimized B4, with one slower
  pair; it was not promoted.
- Fixed HIP/hipBLASLt algorithm 3903 passed all 80 B16 FFN projections and full
  output equality. Warm forward improved 1.0163x, but incremental E2E was only
  1.0021x for 16 inputs and 1.0041x for 64 inputs, with mixed resident results.
  All 480 prediction archives matched official same-group outputs. The default
  remains unchanged. See [B16 FFN evidence](docs/esmc-b16-ffn.md).

The tested exact-output tuning directions have reached small E2E returns.
Future experiments should require a new measured bottleneck or kernel hypothesis,
then real-activation parity, all-layer checks and complete paired E2E validation.
